# Technology plan

**October 2026.** Technology includes tools, systems, algorithms, input/output
and ethical decisions, not only screens. Computer science is not synonymous
with consuming an app. Actual school accounts, licenses, privacy approvals,
device counts, Wi-Fi and loan availability are **VERIFICATION REQUIRED**.

## Four requirement labels

| Label | Meaning | Appropriate example |
|---|---|---|
| **None** | No digital device needed for the stated objective | Observe/model/measure; compose a body-percussion phrase; follow and debug a paper algorithm |
| **Optional** | Device changes convenience, not the demonstrated objective | Teacher photographs a model instead of drawing; optional document camera with real-object demonstration alternative |
| **Recommended** | Device adds educational value but the same objective can still be evidenced without it | Large data set graphing when a manageable paper data set preserves the taught interpretation criterion |
| **Required** | Stated objective cannot be demonstrated without the actual digital/programmable device | Run/debug a Scratch program; operate a programmed robot or sensor; test an interactive input controller |

Each lesson names the device/app version, compatible access, why it is needed,
quantity/turns, prep test and fallback. Electricity using protected AA packs
does not require a screen. Digital art is not the only arts route: observational
drawing, model form, composition, rhythm and performance are authentic A.

## Objective-preserving vs objective-changing alternatives

| Learning purpose | Usual label | No-device route | Evidence limit |
|---|---|---|---|
| Sequence, loops, conditions, decomposition, debugging concepts | None | Large arrow cards, desk grids, repeated actions or sorting rules | Evidence of computational thinking; not proof that software executed |
| Closed path/input-output in simple circuits | None | Preflight-approved Snap Circuits in selected OLP lessons, or the separate protected-AA route | Paper circuit diagram alone does not prove building/testing an electrical circuit |
| Science observation, temperature, structures, measurement | None | Physical objects, non-glass tools, individual show/tell/data | A teacher demo alone does not evidence every student's investigation |
| Observation/composition/pattern/music objective | None or Optional | Paper design and sound/silence phrase with body percussion | If objective specifically concerns a digital tool, paper changes it |
| Evidence documentation/presentation | Optional | Draw/label/model/orally explain | Personal recording devices are not prerequisites |
| Research/data interpretation | Recommended only with justification | Teacher-vetted printed/text read-aloud source; small supplied data set | Online source-evaluation objective requires appropriate actual online examples/access |
| Scratch/ScratchJr executable program | Required | Plan/trace/debug on paper now; schedule executable program later | Mark execution objective NE/deferred; never record programming mastery from paper |
| Dash/Sphero/Ozobot or sensor-controlled behavior | Required | Predict/trace algorithm using pointer on grid | Robot operation, sensing and live debugging require working compatible equipment later |
| Standalone stored-program floor robot | Required for execution | Large paper sequence while unit is unavailable | Optional enhanced purchase; no host assumed only after product verification |
| USB input/Makey Makey/modular app-linked project | Required where digital response is O1 | Draw input/output model or use AA circuit for a different O1 | Different objective explicitly recorded; proprietary power components never improvised |

If the technology fails: try the lesson's **pretested** basic restart/connection
steps briefly, then protect teaching time and switch to a named fallback.
Do not create personal accounts, bypass protections, install unknown software
or download unapproved materials during class. Record what objective changed,
what was actually demonstrated and when the missing evidence will be collected.

## Access, capacity and sustainability

Default maximum team size three: 10/15/20/25 pupils need 4/5/7/9 working team
devices. Each student needs an execution/debugging turn for individual evidence.
If there are only four devices for 25, plan nine teams in three rotations,
each with a specified test/reset time and meaningful non-device work; schedule
additional meetings if native 25/30/40/45 minutes cannot include every turn,
assessment and cleanup. Do not equate watching another group with mastery.
Account accessibility and sensory/motor supports must be confirmed.

The [materials budgets](./Materials_Plan.md) fund no managed tablet/computer or
licensed app. Enhanced robots are a conditional option, not a promise of
Dash/Sphero/EV3 availability. HOST/DASH/SPHERO/MODULAR/INPUT database rows are
legacy inventory questions. Verify loan contents, dates, chargers, missing
pieces, age ratings, host compatibility, app availability/support and all fees
before selecting a device-dependent lesson.

## Before any app or online service

| Verification required | Responsible school role to assign | Evidence to retain locally |
|---|---|---|
| Existing managed device count/condition, chargers, compatible OS | [Technology lead] | Asset count and dated trial |
| Cost/free license terms, education eligibility, offline capability | [Purchasing/technology lead] | Current vendor terms and tested function |
| Age terms, accounts, data collected, retention/deletion, consent | [Administrator/privacy lead] | Actual approval under school policy |
| Access restrictions, advertisements, public sharing and accessibility | [Teacher/technology lead] | Classroom configuration and fallback |
| Student images/names/work and family permission | [School-approved contact] | Verified school consent process, not assumed consent |
| Loan inventory and return/transportation terms | [Loan coordinator] | Confirmed booking, complete kit and dates |

Scratch, ScratchJr, Code.org, Chrome Music Lab, Canva, Tinkercad and robot apps
are legacy candidates, **not guaranteed free/approved/installed services**.
Use current vendor information for verification; this plan creates no school
account or privacy policy. No student data are uploaded as part of this review.
Use the [external-service approval register](External_Service_Approval_Register.csv)
for the currently named platforms. Every row is held until a school reviewer
records current terms, privacy, accessibility, supported versions, pretest, and
approval evidence.

required even when the digital-technology label is None. Use the
[generated lesson map](Lesson_Map.csv) for subsequent updates.

Use actual paths, schedules and rotations to connect material/host questions.
Keep objective-preserving and objective-changing fallback fields distinct.

approval or safe equivalent substitution. Confirm Ozobot/EV3/other proprietary
platforms separately rather than pricing them as the generic floor robot.

screen. Actual app/device inventory, licenses, compatibility, semantic teacher
review, local release and observed outcomes remain unverified.
No school holding is inferred from a name or an access resource.
